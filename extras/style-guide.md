## 團隊程式碼規範

### 命名

- 變數與函式名稱用小駝峰，例如 `readRecords`、`daysSince`，不要用底線分隔。
- 常數用全大寫加底線，例如 `MAX_RETRY_COUNT`，而且只用在真的不會變的值。
- 類別名稱用大駝峰，例如 `MaintenanceReport`，檔名則用小寫加連字號。
- 布林變數用 is、has、can 開頭，例如 `isOverdue`、`hasRecord`，讀起來像一個問句。
- 函式名稱用動詞開頭，說清楚它做什麼，例如 `parseRecords`，不要只寫 `records`。
- 不要用單一字母當變數名稱，迴圈索引的 i、j 除外。
- 縮寫只用大家都懂的，例如 id、url、csv，自己發明的縮寫一律寫完整。
- 同一個概念在整個專案只用一個名字，例如機台一律叫 machine，不要一下 device 一下 equipment。
- 集合用複數，單筆用單數，例如 `records` 跟 `record`。
- 時間相關的變數名稱要帶單位，例如 `timeoutMs`、`limitDays`，不要只寫 `timeout`。

### 格式

- 縮排用兩個空白，不要用 Tab。
- 字串一律用單引號，只有字串裡本身有單引號時才改用雙引號。
- 每行不超過 100 個字元，超過就換行，換行時運算子放在新一行的開頭。
- 每個敘述結尾都加分號，不要依賴自動補分號。
- 物件與陣列的最後一個元素後面加逗號，這樣新增一行時 diff 比較乾淨。
- 檔案結尾要有一個空行。
- 不同用途的程式碼區塊之間空一行，同一件事的程式碼不要拆開。
- import 或 require 統一放在檔案最上面，依序是內建模組、第三方套件、專案內的模組。
- 匯出統一寫在檔案最後，不要散落在各個函式定義的地方。
- 不要留下被註解掉的舊程式碼，要找回來就看版本紀錄。

### 註解

- 每個檔案開頭用一行註解說明這個檔案負責什麼。
- 每個匯出的函式上方寫一行中文註解，說明用途、參數的意義與回傳值。
- 註解寫為什麼這樣做，不要寫程式碼本身已經講清楚的事。
- 有特殊處理的地方一定要註解原因，例如「空白日期視為從未保養，所以要列出來」。
- 暫時性的處理要標明 TODO，並寫上負責人跟預計處理的日期。
- 註解跟程式碼不一致的時候，以程式碼為準，並且順手把註解改正。
- 不要在註解裡寫個人情緒或抱怨。

### 錯誤處理

- 錯誤訊息用繁體中文，要寫出發生什麼事跟可能的原因，例如「第一行不是欄位名稱」。
- 不要吞掉例外，catch 之後至少要記錄下來或重新拋出。
- 檔案讀不到、格式不對這類可以預期的錯誤，要給使用者看得懂的訊息。
- 不可預期的錯誤直接拋出，讓呼叫的人決定怎麼處理。
- 輸入資料先檢查再使用，不要假設外部資料一定是對的。
- 回傳值的型別要一致，不要有時候回傳陣列、有時候回傳 null。
- 找不到資料時回傳空陣列，不要回傳 undefined。
- 數字解析失敗時要明確處理，不要讓 NaN 一路傳下去。

### 日期與時間

- 日期一律用 `YYYY-MM-DD` 字串表示，不要引入日期套件。
- 比較日期前先轉成 Date 物件，不要直接比字串。
- 「今天」由呼叫的人傳進來，函式裡不要直接取現在時間，這樣才方便測試。
- 天數一律用整數，計算時無條件捨去。
- 沒有日期的資料用 null 表示，不要用空字串或 0。
- 時區一律以台灣時間為準，有例外要在註解寫清楚。
- 顯示給使用者看的日期格式，跟資料裡存的格式分開處理。

### 資料處理

- CSV 的欄位名稱維持原本的中文，不要翻成英文。
- 機台編號、廠區代號都維持原樣，不要轉大小寫，也不要去掉前面的零。
- 讀進來的資料先轉成物件陣列，後面的處理都用物件，不要一直用索引取欄位。
- 陣列操作優先用 filter、map、reduce，不要用 for...in 走訪陣列。
- 不要直接修改傳進來的陣列或物件，需要修改時先複製一份。
- 篩選條件寫成獨立的函式，方便測試跟重複使用。
- 大檔案用串流讀取，不要一次把整個檔案讀進記憶體。
- 資料的欄位順序不要寫死在程式裡，用欄位名稱去對應。
- 重複出現的資料轉換寫成共用函式，不要每個地方各寫一次。

### 函式設計

- 一個函式只做一件事，名稱講不清楚它做什麼，就代表該拆了。
- 函式參數超過三個時改用一個物件傳入。
- 有預設值的參數放在最後面。
- 函式長度盡量不超過 40 行。
- 避免巢狀超過三層的 if，能提早 return 就提早 return。
- 純計算的函式不要有副作用，不要在裡面讀檔、寫檔或印東西。
- 會讀檔或寫檔的函式，跟做計算的函式分開。

### 測試

- 測試用 `node:test`，放在 `test/` 目錄，檔名是 `<模組名>.test.js`。
- 測試名稱用中文描述行為，例如「沒有保養日期的機台也會列出來」。
- 每個測試只驗一件事。
- 測試資料寫在測試檔裡，不要另外開檔，除非是在測試讀檔本身。
- 不要在測試裡讀網路資源或依賴外部服務。
- 邊界情況一定要測，例如空陣列、日期空白、剛好等於門檻值。
- 新增或修改函式時，同時補上或修改對應的測試。
- 不要刪除既有的測試，測試失敗時先找原因。
- 改完程式要跑 `npm test`，確認全部通過再回報。
- 測試裡用到的「今天」一律寫死成固定日期，例如 2026-09-30。

### 檔案與目錄

- 程式放在專案根目錄或 `src/`，測試放在 `test/`，資料放在 `data/`。
- 不要修改 `data/` 目錄裡的檔案，那是範例資料。
- 一個檔案只放一個主要的模組。
- 檔案超過 300 行就考慮拆開。
- 設定值集中放在一個地方，不要散落在各個檔案。
- 產生出來的檔案不要放進版本控制。

### 相依套件

- 這個專案只用 Node.js 內建功能，不要加任何第三方套件。
- 真的需要新套件時，先在團隊討論，說明為什麼內建功能做不到。
- 不要自行升級 Node.js 版本。
- 不要新增 package.json 的 scripts，現有的 `npm test` 就夠用。

### 版本控制

- commit 訊息用繁體中文，第一行不超過 50 個字，說明改了什麼。
- commit 訊息的第二段說明為什麼要改。
- 一個 commit 只做一件事，不要把不相關的修改混在一起。
- 不要一次改太多檔案，改動大的時候拆成幾個 commit。
- 推上去之前先跑過測試。
- 不要把密碼、金鑰、個人資料放進版本控制。

### 程式碼審查

- 送審之前自己先看過一次 diff。
- 審查意見對事不對人，說明哪裡有問題跟建議怎麼改。
- 看不懂的地方直接問，不要猜。
- 審查通過之後才合併，不要自己合併自己的修改。
- 審查時特別注意錯誤處理、邊界情況跟測試有沒有補。

### 效能

- 先寫出正確的版本，有量測數據證明太慢再優化。
- 迴圈裡不要重複做同樣的計算，算一次存起來。
- 不要在迴圈裡讀檔。
- 資料量大的時候，先篩選再排序。

### 安全

- 不要把使用者輸入直接拼進指令或檔案路徑。
- 讀取檔案時確認路徑在專案目錄裡面。
- 錯誤訊息不要洩漏內部路徑或系統資訊。
- 記錄檔裡不要寫入個人資料。

### 文件

- README 用繁體中文，說明這個專案做什麼、怎麼安裝、怎麼執行測試。
- 新增函式時，同步更新 README 的函式列表。
- 範例要能直接複製執行。
- 規格有變動時，文件跟程式一起改。

### 跟 AI 協作

- 交辦之前先把需求想清楚，寫出要做什麼、做到什麼程度算完成。
- 一次只交辦一件事，做完確認了再給下一件。
- AI 改完的程式一定要自己看過，也要跑過測試。
- 不清楚的地方請 AI 先列出假設再動手。
- 回報時請 AI 列出改了哪些檔案跟測試結果。
- 不要把公司的機密資料貼給外部的 AI 服務。

### 日誌與記錄

- 用統一的記錄函式，不要到處直接 `console.log`。
- 記錄分成資訊、警告、錯誤三個等級，正式環境只輸出警告以上。
- 每一筆記錄都要帶時間、等級、來源模組跟訊息。
- 記錄訊息用繁體中文，關鍵的值用「欄位名稱=值」的格式寫出來，方便搜尋。
- 處理大量資料時，記錄筆數跟耗費的時間，不要每一筆都記。
- 不要留下除錯用的記錄，送審前全部拿掉。

範例：

```javascript
// 好的寫法：有等級、有來源、有關鍵的值
log.warn('maintenance', `找不到保養日期 機台編號=${record.id} 廠區=${record.site}`);

// 不好的寫法：看不出是誰印的、在什麼情況下印的
console.log('沒有日期', record);
```

### 設定與環境變數

- 會因環境不同而改變的值，例如檔案路徑、門檻天數，放在設定檔或環境變數裡。
- 環境變數的名稱用全大寫加底線，並且加上專案前綴，例如 `MAINT_LIMIT_DAYS`。
- 讀不到必要的設定時，啟動時就直接報錯，不要等到用到才出錯。
- 每個設定都要有說明跟預設值，寫在 README 的設定章節。
- 不同環境的設定檔分開放，不要在程式裡用 if 判斷環境。

範例：

```javascript
// 讀取門檻天數，沒設定就用 90 天，設定了但不是數字就直接報錯
const raw = process.env.MAINT_LIMIT_DAYS ?? '90';
const limitDays = Number(raw);
if (!Number.isInteger(limitDays) || limitDays <= 0) {
  throw new Error(`MAINT_LIMIT_DAYS 必須是正整數，目前的值是 ${raw}`);
}
```

### 資料檔格式

- CSV 第一行一定是欄位名稱，欄位之間用半形逗號分隔。
- 欄位值裡不要出現逗號，真的需要時整個值用雙引號包起來。
- 檔案編碼一律用 UTF-8，不要用 Big5。
- 換行字元一律用 LF，不要用 CRLF。
- 空白的欄位留空就好，不要填「無」、「N/A」或 0。
- 檔名包含資料的年月，例如 `maintenance-2026-09.csv`，方便知道是哪一期的資料。
- 新增欄位時加在最後面，不要插在中間，舊的程式才不會讀錯欄位。

### 發布與部署

- 發布前先在測試環境跑過一次完整流程。
- 每次發布都要有版本號，版本號照「主版本.次版本.修訂版」的規則。
- 發布說明用繁體中文，列出新功能、修正的問題跟需要注意的地方。
- 有破壞相容性的修改，一定要在發布說明裡標出來，並說明怎麼調整。
- 發布出問題時，先退回上一版，再找原因。

### 撰寫文件的語氣

- 用台灣繁體中文，不要用中國用語，例如「文件」不要寫成「文檔」、「最佳化」不要寫成「優化」。
- 中文內文用全形標點，程式碼、網址、英文片段保留半形。
- 句子寫短一點，一句話只講一件事。
- 步驟用編號列出來，每一步只做一個動作。
- 專有名詞第一次出現時，用一句白話解釋。
- 不要寫「很簡單」、「顯然」這類詞，讀的人不一定覺得簡單。

### 報表輸出

- 報表的欄位順序固定：機台編號、廠區、上次保養日期、距今天數、狀態。
- 狀態只有三種：正常、即將逾期、已逾期，不要自己發明其他說法。
- 天數為空白的機台，距今天數欄位顯示「無紀錄」，狀態一律是已逾期。
- 數字靠右對齊，文字靠左對齊。
- 報表最上面寫產生的時間跟使用的門檻天數，看報表的人才知道標準是什麼。
- 同一份報表依廠區排序，同一個廠區裡再依距今天數由大到小排序。
- 輸出成 CSV 時，欄位名稱用中文，跟讀進來的資料一致。
- 報表檔名包含產生的日期，例如 `overdue-report-2026-09-30.csv`。

範例：

```plaintext
產生時間：2026-09-30 09:00
門檻天數：90

機台編號  廠區  上次保養日期  距今天數  狀態
EQ-1013   L6B   2026-04-11         172  已逾期
EQ-1002   L5A   2026-06-02         120  已逾期
EQ-1020   L8C                   無紀錄  已逾期
```

### 命令列工具

- 每支命令列工具都要支援 `--help`，印出用法、參數說明跟範例。
- 參數名稱用小寫加連字號，例如 `--limit-days`，不要用底線。
- 必要的參數沒給時，印出錯誤訊息跟用法，並以非 0 的結束碼結束。
- 正常的輸出印到標準輸出，錯誤訊息印到標準錯誤，方便別人串接。
- 執行成功時結束碼是 0，失敗時是 1，不要回傳其他數字，除非有在 `--help` 裡說明。
- 會修改檔案的工具，預設先列出會做什麼，加上 `--yes` 才真的執行。
- 執行時間超過幾秒的工具，要印出進度，讓使用的人知道它還在跑。

範例：

```plaintext
用法：node scripts/report.js [選項]

選項：
  --limit-days <天數>   超過幾天沒保養算逾期，預設 90
  --site <廠區>         只列出指定廠區，例如 L5A
  --output <檔名>       輸出成 CSV 檔，不給就印在畫面上
  --help                顯示這段說明
```

### 會議與溝通

- 需求有變動時，在 issue 裡留下紀錄，不要只在口頭或聊天訊息裡講。
- issue 的標題寫清楚要做什麼，內文寫為什麼要做、做到什麼程度算完成。
- 發現別人的程式有問題，開 issue 或在審查時提出，不要直接改掉不說。
- 卡住超過半天就找人討論，不要一個人一直卡著。
- 每週固定看一次待處理的 issue，關掉已經完成或不需要的。

### 常見問題

- 問：規範跟現有的程式碼不一致時，要照哪一個？
  答：新寫的程式照規範。舊的程式碼不要為了規範特地改，等到有修改那個檔案的機會時再一起調整，並且在 commit 訊息裡說明。
- 問：規範沒有寫到的情況怎麼辦？
  答：先參考專案裡已經有的寫法，保持一致。真的找不到前例，就在團隊頻道提出來討論，討論的結果補進這份規範。
- 問：趕時間的時候可以先不寫測試嗎？
  答：不行。至少要有一個測試證明主要的功能是對的，邊界情況可以開 issue 之後補，但 issue 要寫清楚缺了哪些。
- 問：AI 產生的程式碼也要照這份規範嗎？
  答：要。不管是誰寫的，進到專案裡的程式碼都照同一份規範審查。交辦給 AI 的時候，可以把相關的段落一起附上。
- 問：這份規範多久更新一次？
  答：每一季檢查一次，有人提出修改建議時也可以隨時更新。每次更新都要在最上面註明日期跟改了什麼。
